# `rvs` 0.4.5

`rvs` 0.4.5 makes Linux installation and interactive credential storage
explicit across desktop, server, WSL, and CI environments.

## Added

- Interactive login supports the detected OS keyring and an initialized
  `pass` store. `--credential-store`, `RVS_CREDENTIAL_STORE`, and
  `rvs auth keyring set` provide explicit selection when both are present.
- `rvs auth keyring doctor` reports every supported provider and performs a
  disposable write/read/delete test without exposing stored credentials.
- Non-Debian glibc `amd64` systems receive a rootless portable installation
  path with a signed release inventory and exact archive checksum verification.
- Source CI exercises the frozen bundle on pinned Ubuntu, Debian, Fedora,
  RHEL-compatible, Amazon Linux, openSUSE, and Arch Linux images.

## Changed

- Device authorization starts only after the selected credential provider
  passes its storage preflight. The successful provider is pinned to the
  profile and preserved across logout.
- Access and refresh credentials are treated as one pair. Failed local writes
  remove partial state and revoke a newly issued refresh token; refresh rotation
  applies the same rollback rule.
- `RVS_TOKEN` bypasses local credential-provider discovery for headless and CI
  use. The CLI never falls back to plaintext credential files.
- Debian, Ubuntu, WSL, and Debian-family derivatives continue using the signed
  APT channel. Other supported glibc distributions use the signed portable
  archive and install under the user's home by default.

## Known gaps

- Alpine/musl, Linux `arm64`, and NixOS do not yet have native artifacts. The
  installer rejects these targets before downloading an incompatible binary.
- GNOME and KDE login-session behavior still requires VM-based release
  certification because minimal containers cannot model PAM unlocking and a
  user's graphical D-Bus session.

## Compatibility

This maintenance release stays on the `v0.4` APT compatibility channel. Existing
profiles and legacy OS-keyring credentials remain compatible. Automation using
`RVS_TOKEN` requires no migration.
